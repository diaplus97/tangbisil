# 온라인 탕비실 — 게임 리디자인 기준 문서

> v0.3 작업의 기준 문서. 코드보다 이 문서가 먼저다.
> 여기 적힌 수치와 규칙을 코드가 따르고, 바뀌면 이 문서를 먼저 고친다.

---

## 0. 이 문서를 쓰는 이유

v0.2까지는 기준 없이 컴포넌트를 하나씩 붙여서 만들었다. 그 결과 화면이 "픽셀 장식이 붙은 웹페이지"가 됐고, 모바일은 데스크탑 레이아웃을 억지로 축소한 형태가 됐다. v0.3은 방향을 먼저 고정하고 거기에 코드를 맞춘다.

---

## 1. 현재 진단 — 무엇이 "게임 같지 않은가"

### 1.1 플레이어가 사물이다 ← 가장 큰 문제

지금 나는 **카운터 위에 놓인 컵**이다. 움직일 수 없고, 위치가 없고, 다른 사람과의 거리도 없다. 컵들은 그냥 가로로 나열된다. 이건 게임이 아니라 접속자 목록에 가깝다.

게임의 최소 조건은 **내가 조작하는 무언가가 공간 안에 있는 것**이다.

### 1.2 모바일이 데스크탑의 축소판이다

데스크탑 3열 그리드(좌 사이드바 / 중앙 / 우 사이드바)를 390px 폭에 그대로 넣었다. 그 결과 좌우 컬럼이 각각 72~112px로 눌리고, 폰트가 7~11px까지 내려가고, 오브젝트는 0.68배로 축소된다. **읽을 수 없는 게 당연하다.**

### 1.3 상호작용이 전부 같은 동사다

만두·디저트·자판기·화분이 전부 "탭 → 정해진 대사 출력"으로 끝난다. 시각적 연출(v0.2에서 개선)은 좋아졌지만 **동사가 하나**라 두 번째부터 할 이유가 없다.

### 1.4 프리셋 대사가 중복이다

하단 프리셋 버튼 7개는 상호작용이 이미 만들어내는 대사와 겹친다. 화면 아래 40%를 차지하면서 새로운 걸 주지 않는다. → **제거.**

---

## 2. 설계 원칙

1. **모바일이 기준.** 데스크탑은 모바일 화면을 크게 보여주는 것으로 족하다. 반대로 하지 않는다.
2. **플레이어는 공간 안의 캐릭터다.** 위치가 있고, 걷고, 거리가 의미를 갖는다.
3. **한 화면에 다 있다.** 스크롤 없음. 방 하나가 곧 게임 전체.
4. **오브젝트는 목적지다.** 버튼이 아니라 "가서 쓰는 것". 다가가야 쓸 수 있다.

---

## 3. 화면 — 고정 스테이지 + 스케일

픽셀 게임의 방식. 방을 **고정 논리 해상도**로 그리고 화면에 맞춰 통째로 확대한다.

| 항목 | 값 |
|---|---|
| 논리 해상도 | **340 × 540** (세로) |
| 스케일 | `min(가용폭 / 340, 가용높이 / 540)` |
| 렌더링 | `image-rendering: pixelated`, `transform: scale()` |

**왜 세로 고정인가**: 폰이 기준이고, 폰은 세로다. 데스크탑에서는 방이 화면 중앙에 세로로 놓이고 주변은 여백(벽지 톤)으로 채운다. 하나의 레이아웃만 유지되므로 "모바일에서만 깨지는" 문제가 구조적으로 사라진다.

**화면 구성 (위 → 아래)**

```
┌─────────────────────────┐
│ 상태바 (40px 고정)       │  닉네임 · 접속자 수 · 소리 토글
├─────────────────────────┤
│                         │
│      방 스테이지         │  340 × 540 논리, 스케일되어 표시
│    (여기가 게임 전부)     │
│                         │
├─────────────────────────┤
│ 액션바 (72px 고정)       │  상황별 액션 버튼 + 채팅 입력
└─────────────────────────┘
```

기대 스케일: iPhone(390 폭) → **약 1.15배**. 즉 논리 12px 글자가 실제 약 14px. 지금(7~11px)보다 확실히 크다.

## 4. 방 좌표계 & 배치

원점은 좌상단. 캐릭터의 `(x, y)`는 **발이 닿는 바닥 지점**을 뜻한다.

```
 0                                                    340
 ├──────────────────────────────────────────────────────┤
 0  ╔══════════════════════════════════════════════════╗
    ║  천장 몰딩                                        ║  28
    ║                                                  ║
    ║   ┌────┐      ┌──┐         ┌──────────┐         ║
    ║   │창문│      │시계│        │  게시판   │         ║  50~118
    ║   └────┘      └──┘         └──────────┘         ║
    ║                                                  ║
    ║            ┌──────────┐                          ║
    ║            │ 디저트선반 │                          ║  168~206
    ║            └──────────┘                          ║
    ║  ┌──────┐                          ┌────────┐   ║
    ║  │ 커피  │   ┌────────┐            │        │   ║
    ║  │ 머신  │   │전자레인지│            │ 자판기  │   ║  ~240
280 ║══╧══════╧═══╧════════╧═══ 카운터 ═══│        │   ║  카운터 상판
    ║                                    │        │   ║
330 ╠════════════════════════════════════╧════════╧═══╣  바닥 시작
    │                                                  │
    │              ●  ← 캐릭터 (발 기준)                 │
    │                                              🪴   │
    │                                                  │
540 └──────────────────────────────────────────────────┘
```

### 주요 경계

| 이름 | 값 | 의미 |
|---|---|---|
| `FLOOR_TOP` | 330 | 벽/바닥 경계 |
| `COUNTER_TOP` | 280 | 카운터 상판 y (오브젝트가 여기 올라섬) |
| `COUNTER_RIGHT` | 244 | 카운터 우측 끝 |
| `WALK` | x 16~324, y 356~512 | 캐릭터 이동 가능 범위 |

### 오브젝트 배치

| 오브젝트 | 그려지는 위치 | 서는 지점 (stand) | 상호작용 |
|---|---|---|---|
| 커피머신 | x 26~96, y 188~280 | (58, 366) | 커피 내리기 → 자리 잡기 |
| 전자레인지 | x 112~192, y 236~280 | (150, 366) | 만두 데우기 (8초) |
| 디저트선반 | x 120~212, y 168~206 | (200, 370) | 쿠키/도넛/초콜릿 |
| 자판기 | x 262~326, y 240~344 | (292, 372) | 동전 → 음료 |
| 화분 | x 288~322, 바닥 y 505 | (300, 470) | 물 주기 |
| 창문 | x 22~104, y 52~118 | — | 장식 (실시간 날씨) |
| 시계 | x 130~178, y 56~92 | — | 장식 (현재 시각) |
| 게시판 | x 206~306, y 48~104 | — | 장식 (뉴스/앰비언트) |

**깊이감**: 뒤쪽(작은 y)에 있을수록 캐릭터를 작게 그린다 — `scale = 0.86 ~ 1.14`. z-index는 y 순서(앞에 있는 캐릭터가 위에 그려짐).

## 5. 캐릭터

- 크기: **22 × 36** 논리 픽셀 (깊이 스케일 적용)
- 구성: 머리 / 머리색 / 몸(셔츠) / 다리 / 신발
- 외형은 닉네임 해시로 결정 → 같은 사람은 항상 같은 모습
- 커피를 내리면 **컵을 든 모습**으로 바뀐다 (자리 잡음의 시각적 표현)
- 걷기: 2프레임(다리 교차) + 방향에 따라 좌우 반전

## 6. 이동

- **바닥을 탭하면 그 지점으로 걸어간다.** (조이스틱 없음 — 폰에서 화면을 가리지 않는 게 우선)
- 속도 78 논리px/초 (방 세로를 약 2.5초에 횡단)
- 오브젝트를 탭하면 그 오브젝트의 **stand 지점으로 걸어가서** 자동으로 액션 버튼이 뜬다
- 도착하면 멈춘다. 관성·충돌 없음.

## 7. 상호작용 모델

```
바닥/오브젝트 탭  →  걷기  →  도착  →  액션바에 큰 버튼 등장  →  탭  →  연출 + 대사
```

- 가장 가까운 대상 하나만 잡는다 (`REACH = 42` 논리px)
- 범위를 벗어나면 버튼이 사라진다
- **커피를 내리기 전에는 다른 오브젝트를 쓸 수 없다** (기존 규칙 유지 — 자리 잡기가 곧 입장)

## 8. 대화

- 프리셋 버튼 **제거**
- 액션바에 입력창 하나 (최대 30자)
- 보낸 말은 **내 캐릭터 머리 위 말풍선**으로 뜬다 (6초)
- 상호작용 대사도 같은 말풍선으로 나온다 → 채널이 하나로 통일됨
- 말풍선은 캐릭터를 따라다닌다 (지금처럼 별도 레이어에 겹침 정렬하지 않음)

## 9. 존재감 — 빈 방 문제

동접이 0이어도 방이 비어 보이면 안 된다.

- **식은 컵**: 다녀간 사람의 컵이 카운터 위에 회색으로 남는다 (최대 4개 + `+n`)
- **고양이 "탕비"**: 바닥을 어슬렁거리는 상주 NPC. 탭하면 골골송
- 상태바에 "지금 3명 · 오늘 12명 다녀감"

v0.2에서 만든 Web Audio 합성 엔진(`src/lib/sound.ts`)을 그대로 쓴다. 오디오 파일 0개.

## 11. 데이터 모델 & 동기화

기존 Supabase `cups` 테이블을 확장한다. **위치는 "목표 지점"만 저장**하고 걷는 모습은 각 클라이언트가 보간한다 → 탭할 때만 쓰기가 일어나므로 쓰기 빈도가 매우 낮다.

```sql
alter table cups add column if not exists x real;
alter table cups add column if not exists y real;
```

| 컬럼 | 용도 |
|---|---|
| `id` | 세션 ID (localStorage 고정) |
| `nickname`, `color` | 외형 |
| `x`, `y` | **목표** 위치 (도착점) |
| `coffee_type` | 자리 잡음 여부 + 컵 종류 |
| `message`, `message_at` | 말풍선 |
| `left_at` | 식은 컵 마킹 |

Supabase 미설정 시 지금처럼 오프라인 데모 모드 (혼자 걸어다니며 다 해볼 수 있음).

## 14. 결정이 필요한 것 ⚠️

### Q1. 이 게임의 "목표"는 무엇인가

지금은 목표가 없는 **행아웃(hangout)**이다. Phase 3까지 하면 "예쁘고 쾌적한 행아웃"이 된다. 그걸로 충분한지, 아니면 진행감이 필요한지 결정이 필요하다.

- **A. 순수 행아웃** — 목표 없음. 사람이 있는 것 자체가 콘텐츠. (예: Gather.town)
  - 장점: 만들기 쉽고 세계관에 맞음
  - 단점: **동접이 없으면 할 게 없다** — 초기 트래픽 문제에 취약
- **B. 가벼운 수집** — 음료·간식 도감, 출근 도장, 꾸미기 아이템 해금
  - 장점: 혼자 와도 할 게 있음. 나중에 아이템 판매로 이어짐
  - 단점: 자칫 "출석 체크 앱"이 됨
- **C. 미니게임 내장** — 커피 내리기 타이밍 게임, 만두 굽기 등 실제 조작 게임
  - 장점: 확실히 "게임"이 됨
  - 단점: 탕비실의 느긋한 정서와 충돌할 수 있음

### Q2. 캐릭터를 꾸밀 수 있는가

꾸미기가 있으면 수익 모델(아이템 판매)로 직결되고, "내 캐릭터"라는 애착이 생긴다. 대신 외형 데이터 동기화와 에디터 UI가 추가된다.

### Q3. 방이 하나인가, 여러 개인가

사람이 많아지면 한 방에 다 넣을 수 없다. 방 분리(자동 매칭) 또는 "우리 회사 탕비실"(비공개 방) 개념이 필요해질 수 있다. 후자는 유료화 포인트가 될 수도 있다.
